## What it teaches

Four bridges between Claude Code sessions and external surfaces: iMessage texts (macOS only), native desktop control on macOS, remote steering of a session from any browser, and a unified command-line interface to Google Workspace services with pre-built automation skills. The channel pattern (events pushed into a running session) differs from Proteus's stateless scheduled tasks.

## Tools they use

iMessage channel plugin: https://github.com/anthropics/claude-code (included in Claude Code, requires bun and full-disk-access permission).
/computer command and computer-use feature in Claude Code desktop (macOS only, research preview, Pro/Max plans).
/remote-control command (generates session QR code, works from phone or any browser, requires internet and running local session).
Google Workspace CLI (gws): https://github.com/googleapis/google-cloud-cli or the open-source repo (beta, not officially supported, auto-discovers new Google APIs).

## What Proteus already has that does the same job

Screenshot + click via Playwright and headless browsers: Proteus has this via the browser tools for any site, plus Safari restrictions do not affect it.
Unattended automation: Proteus uses scheduled tasks and the PreToolUse hook (stricter than the auto-mode classifier in the videos), not interactive sessions that must stay awake.
Email and text bridging: Proteus sends one weekly Field Notes email via bin/send-field-notes.sh. The charter forbids other outbound messages. Listening to iMessage would violate that rule (charter: "one weekly email to Luke through bin/send-field-notes.sh. Nothing else is sent to anyone").
Google services integration: the toolshelf has Google Places API (T-0080) and Keyword Planner (T-0081), but no unified CLI. No Proteus desk uses Google Docs, Sheets, Calendar or Gmail.

## What we would need to fetch

Google Workspace CLI from GitHub (free, beta, open-source). iMessage channel is included with Claude Code. Remote control is built-in. No accounts or spend needed for the tools themselves, but iMessage requires a macOS machine and remote control requires internet.

## One thing worth trying

Read the iMessage channel plugin source code and sketch a design for a Slack or Discord variant (20 minutes in sandbox/, no account needed, just source inspection). The output is a one-page diagram of the event flow (how a text becomes a tool call, where permissions go) and one design choice that differs from iMessage (e.g. threaded replies, reaction-based approval, or user separation). This teaches whether Proteus could add a similar bridge if the charter changed to allow service-mode work (it does not currently).

## Verdict

SKIP: none of these tools fit Proteus's unattended-first architecture. iMessage and remote control require a running interactive session (Proteus sessions are stateless and fire once per schedule). Computer use is available via Playwright; native macOS control adds little for unattended work. GWS CLI is clean but no Proteus desk needs Google services. The charter forbids outbound messages to Luke except the weekly Field Notes, ruling out an iMessage responder. A significant architecture change (moving to service-mode, always-running sessions) would be needed to adopt any of these, and Luke has not asked for that.
