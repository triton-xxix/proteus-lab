# S-19: Agent J Day 6: newsletter summarizer, base layer, multi-sender categorisation, weekly digest to Slack

Note: three live community calls (62, 60 and 53 minutes), auto-captioned and rough. Roughly half of each call is introductions, Q&A and chat about Claude plans, LinkedIn tools and "open claw". The build itself is a no-code n8n workflow, with Claude in the Desktop app writing every JavaScript snippet and prompt. Nothing was fully working on camera: call 1 ended with an unresolved Notion mapping bug, call 2 had a stray "=" sign in fields.

## What it teaches
- Week 1 pipeline: schedule trigger (daily 8pm) on Gmail, filtered by sender. Then a code node that strips the HTML and truncates the body. Then an LLM chain that returns a summary and three key insights. Then a code node that reshapes the output to the database columns. Then a Notion "create database page" node. Fetch with "simplify" off so the whole email is available.
- Week 2 adds a "smart router" code node (several senders, plus a subject-line filter such as "only Gemini meeting notes with a given keyword"), then a second LLM node that fills fixed fields: category (about six options), priority, email type, action items, extracted links. Temperature is set to 0.2 to 0.3 so the output keeps one structure. A one-off backfill uses Gmail "get many" and runs the nodes by hand in chunks (a 119-email pull had to be cut to 40).
- Week 3 is a separate workflow because one workflow has one trigger: a Monday 8am schedule reads the Notion rows from the last seven days, a code node groups them by sender, one Haiku call writes the digest (per author summary, cross-newsletter links, merged action items, content ideas), and a Slack "send message" posts it to a channel. The prompt was iterated three rounds with Claude after the first output mixed all authors together.
- The method is the real lesson: Notion as the store, Claude connected to Notion to query it later, n8n to move data, Claude to debug by pasting errors or screenshots back. A human stays in the loop for anything sent out under the host's name.
- Cost anecdotes: Haiku 4.5 as the cheap model, about 18 cents for a 50-email backfill, 35 cents for 80 emails with categories, 2.46 dollars for "hundreds" with the digest runs.

## One thing worth trying
Temperature and schema stability on the local model, in /Users/triton/PROTEUS/sandbox/ (about 25 minutes, no keys, no spend). Take 10 existing Proteus items with free text (for example harvest candidates or past Skool digest files). Ask a local Ollama model for a fixed JSON schema (summary, three key insights, category from a fixed list, priority, action items) at temperature 0.2 and at 0.8, five runs each. Score three things per setting: the share of runs that parse as valid JSON with the exact keys, the share where the category stays the same across runs, and wall time. Their claim, that low temperature keeps output structurally the same, is cheap to test, and the result tells Proteus whether a "categorise on arrival" step is worth adding to the harvester using a local model instead of a Sonnet child. Size: small. If no Ollama model is loaded, skip it. I have not checked which models are installed.

## Claims to check
- "300 emails, $1.8" per day (extrapolated from "backfill full for 50 emails, 18 cents"). Arithmetic: 0.18 / 50 = 0.36 cents per email, so 300 emails is about 1.08 dollars, not 1.8. Check by arithmetic, then against current Haiku 4.5 token pricing on Anthropic's pricing page (not looked up here).
- "2.46 for hundreds of emails" (the weekly digest runs and categorisation). Check by running the same email-sized prompt on Haiku through Proteus's existing usage tooling (bin/usage.py) and multiplying out. Per-email cost is the thing to compare with the 18 cent figure, and the two numbers in the transcript do not obviously agree.
- "Lower temperature ... more likely it sticks to the original format". Real in general, but they only describe it and show no measurement. This is the sandbox test above.
- Own judgement, not from the transcripts: the host's statement that one n8n workflow cannot hold two triggers "and they can't live together" is wrong as a general claim (n8n allows several trigger nodes in one workflow). It is what Claude told him. Check by reading n8n's docs only if Proteus ever adopts n8n.
